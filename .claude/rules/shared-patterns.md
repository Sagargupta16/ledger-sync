# Cross-stack patterns

Moved verbatim from the repo `CLAUDE.md` on 2026-10-31; repo-wide rules stay there. Paths and links below are relative to the repo root.

## Architecture

### Key Patterns

- **Auth flow**: OAuth-only (Google, GitHub) with S256 PKCE. No email/password. `GET /api/auth/oauth/providers?flow_version=2` reports configuration; `POST /api/auth/oauth/{provider}/authorize` binds a 10-minute signed state to the provider, challenge, and configured redirect. Unversioned clients receive navigation-only `/api/auth/oauth/v2/{provider}/restart` URLs; the current frontend starts fresh PKCE from that bridge. Missing-verifier callbacks get a readable HTTP 409 refresh/sign-in message, and legacy state is never accepted. The browser tab retains the verifier and consumes its matching `sessionStorage` attempt before callback. The backend atomically consumes the pending `audit_logs` record before provider exchange, including when that exchange subsequently fails. Cross-origin Pages/Vercel sign-in uses no third-party cookies. Immutable provider subjects identify users; verified-email fallback may claim only legacy users whose provider and subject are both null. The callback fetches the profile before installing user and tokens together. `authStore` persists JWTs, `ProtectedRoute` enforces auth, and `useAuthInit` verifies startup state. Logout revokes outstanding token versions and ends the local session. Automation clients use single-scope `lsu_` access tokens (`mmbak:upload`, `ledger:read`, `alerts:ingest`; Settings > Advanced > Access Tokens, five active per scope): each reaches only its route (`POST /api/upload/money-manager`, `POST /mcp`, `POST /api/ingest/text`) and none can sign in.
- **Upload pipeline**: Files are parsed client-side using lazy-loaded SheetJS. The frontend hashes the raw file, maps flexible columns, validates rows, then requires a review of accounts, dates, counts, and complete-ledger scope. Confirmed `TransactionUploadRequest` JSON (`file_name`, 64-character `file_hash`, 1-100,000 `rows`, `force`) goes to `/api/upload`. The backend normalizes and validates every row, with decimal INR amounts required. It commits both transaction/transfer reconciliation and import history as one unit; missing rows are soft-deleted user-wide, including when one ledger group is empty. Analytics runs in a separate transaction and reports ready/failed status. The frontend calls `/api/analytics/v2/refresh` only for an explicit retry, not after every successful upload. The CLI retains the file-based `import_file()` path. A Money Manager `.mmbak` backup takes `POST /api/upload/money-manager` instead: the browser gzips the raw file (Vercel refuses bodies over 4.5 MB), the server reads it, `dry_run=true` previews the changes for the review, an already-imported database returns `unchanged`, and a snapshot that would remove more than max(25, 5%) of live rows returns 409 unless `allow_large_delete=true`. An `mmbak:upload` token (Settings) authenticates only this route, for iOS Shortcuts; it can neither preview nor lift the guard. A backup's repeat rules and monthly budgets also import, linked through `external_refs`: later backups update untouched rows, keep edits made here and never change hand-made rows. A CAS PDF takes `POST /api/upload/cas`: read in memory (4.5 MB cap) with casparser, never stored or logged; a server without the `cas` extra (the hosted one) answers 503. Bank alerts (`POST /api/ingest/text`) never become ledger rows; Data Health matches their stored fields against live rows.
- **Server-side aggregation (v2.17+)**: Analytics pages use rollups (`/api/analytics/v2/*`, `/api/calculations/{totals,monthly-aggregation,category-breakdown}`) and focused read endpoints: `transactions/facets`, `calculations/{quick-insights,data-date-range,income-analysis,category-monthly-history,category-daily-series}`, `analytics/v2/cohort-spending`, and per-request reads from live rows (`dashboard-metrics/{pulse,health}`, `weekly-recap`, `safe-to-spend`, `card-cycles`, `saved-views/tiles`). The Dashboard and Overview no longer download `/api/transactions/all` (about 3.4 MB at 9,000 rows); seven pages still do (Cash Flow, Comparison, GST, Tax, Returns, Investment Analytics, SIP projection). The shared `useAnalyticsTimeFilter` accepts either a transactions array (legacy) or a `{minDate,maxDate}` bounds object (from `data-date-range`). Preference-sensitive tax, GST, net-worth, health-score, and projection calculations still run client-side where needed. Book-value contributions and realised cash events must not be presented as actual market returns. Startup prefetch loads only preferences, active recurring commitments, and Data Health.
- **Capital losses and savings**: Spending aggregates exclude only the EXPENSE rows whose `Category::Subcategory` key the user classified in `capital_loss_categories` (`core/expense_class.py`); nothing is excluded by keyword. Data Health's `capital_loss_candidates` only suggests taxonomies to classify. Net savings = income - spending - classified losses, so a classified loss leaves spending but still reduces savings (the /budgets Savings bucket is the separate investment-perimeter change). Shared metric matchers (essentials, investment accounts, tax paid, investment income, salary/bonus, complete-month averages) live in backend `core/metric_rules.py` and its mirror `frontend/src/lib/finance/metricRules.ts` (+ `lib/finance/monthlyAverage.ts`); change both together so pages, AI tools and demo agree.
- **Goals**: Goal create/edit/progress/allocation/delete persist through user-scoped goal APIs (demo: the page visit only). Never automatically apply or mutate the three old global browser keys: authenticated, non-demo recovery compares recognized fields with the account's fetched positive goal IDs (IDs 1-4 carry a possible-demo warning), needs explicit field selection, ownership confirmation and a separate deletion confirmation, and refetches, guards the session and preserves drafts around writes. Details: [`docs/architecture.md`](docs/architecture.md).
